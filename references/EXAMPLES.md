# AGENTS.md 模板与示例

## 最小起步模板

```markdown
# <项目名称> · 协作约定

<一小段项目简介：项目是什么、为谁服务、Agent 在这里主要做什么、谁说了算。>

## 全局规则

- <取舍优先级：两件事冲突时先保哪个。>
- <哪些操作要先确认；不可违反的红线，附替代做法。>
- <怎么算做完：用什么检查、什么时候跑。>

## 按情境读取

- <进行某类任务时>，读 `<实际文件路径>`，用于 <具体用途>。
```

## 改前改后

一个个人开发的记账 App，假设项目已经在 package.json 中声明了包管理器和常用命令。

改前：

```markdown
# 项目说明

这是一个 Web 应用。请认真、专业地完成任务，保证代码质量。

- 每次开始工作前，先阅读 docs/ 下的所有文档。
- 每次修改代码后，运行全部测试。
- 不要使用 any 类型，不要写重复代码，不要随意引入新依赖。
- 使用 pnpm，启动命令是 pnpm dev，测试命令是 pnpm test。
- 组件放 src/components，接口放 src/api，样式放 src/styles。
- 删除文件前要先确认。
- 记得更新文档。
```

改后：

```markdown
# 记账 App · 协作约定

一个面向个人用户的记账 Web 应用，由我一个人开发。Agent 在这里协助写功能、修 bug、补测试；产品上的取舍由我决定。

## 全局规则

- 使用体验和代码整洁冲突时，先保体验。
- 删除文件、改数据库结构、引入新依赖前，先说明理由，等我确认。

## 按情境读取

- 写代码前读 docs/code-style.md，按其中的类型、复用和文件归位约定来。
- 写或改接口前读 docs/api.md，核对命名与错误码；改完同步更新这份文档。
- 改界面前读 docs/design.md，按其中的组件和间距规范来。
- 改完代码，运行和改动相关的测试；改了公共模块，再跑一遍全部测试。
```

分出去的规则要同时放进对应文件，不能只留下路径。下沉时将模糊要求改成可执行做法，例如把「不写重复代码」写成「新增实现前先查找已有功能；已有实现满足需求时优先复用」。

逐条处理（分类见 SKILL.md「判断标准」）：

| 改前 | 栏位 | 怎么处理 | 为什么 |
| --- | --- | --- | --- |
| 认真、专业、保证质量 | 删除：无效 | 删掉 | 写了也白写 |
| 先读 docs/ 下所有文档 | 下沉 | 换成三条带时机的指针 | 每次全读，大部分任务用不上 |
| 每次改完运行全部测试 | 保留：怎么算做完 | 改成按改动范围跑 | 原句让改一个错别字也跑全套 |
| 不用 any | 下沉 | 移到 docs/code-style.md 的类型约定 | 只在写代码时用到 |
| 不写重复代码 | 下沉 | 改成具体的查找与复用做法，放进 docs/code-style.md | 保留复用要求，改掉空泛表达 |
| 不随意引入新依赖 | 保留：全局规则 | 并入「先说明理由，等我确认」 | 改成要做什么，代价高的操作集中在一条 |
| pnpm 和各个命令 | 删除：一查就准 | 删掉 | package.json 里都有 |
| 目录约定 | 下沉 | 移到 docs/code-style.md | 新文件放哪里是约定，不能只靠列目录推断 |
| 删除前先确认 | 保留：全局规则 | 和改数据库、引入依赖合成一条 | 违反了代价高 |
| 记得更新文档 | 保留：指针 | 写成「改完接口同步更新 docs/api.md」 | 写清更新对象和时机 |
| — | 保留：项目简介 | 新增简介和取舍优先级 | 让 Agent 知道这是什么项目、冲突时先保什么 |

如果「测试必须通过才能合并」或「不允许 any」是硬要求，再加一项「交给工具」：配置测试或 ESLint `no-explicit-any`，在 CI 中执行，并设为合并前必须通过的检查；AGENTS.md 留一句说明。工具未配置时标「待配置」，不能只写一句就当作已经生效。
